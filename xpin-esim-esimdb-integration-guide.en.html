1. Overview#

With the two endpoints in this guide you can fetch the on-sale plans published to you. Plan objects use the DataPlan structure.

Item Description
Endpoints /openapi/v1/products/list (product list), /openapi/v1/products/detail (product detail); see §4
How consumers buy Every plan carries a link to its purchase page, where the consumer completes the purchase
Data structure DataPlan of eSIMDB Provider API v1.0.2; the fields are described in §5

2. Basics#

Item Value
Base URL (sandbox) https://sandboxapi.xpin.network
Base URL (production) https://openapi.xpin.network
Protocol POST for everything, Content-Type: application/json
Charset UTF-8
Success check Read the code field in the response body, not the HTTP status
Credentials app_key / app_secret issued by the platform (obtain them from the platform). Sandbox credentials only work in the sandbox environment

Every business response from the platform is HTTP 200, with this body:

Field Type Description
data object Business data. {} on failure
code number Business code. Only 200 means success
msg string ok on success; an error code or a field-level message on failure
t number Server timestamp in milliseconds. ⚠️ A few server-error responses (406) omit it; do not treat it as always present

🔴 Checking a response takes two steps, not one. If the path prefix is wrong, you used http://, or the connection breaks mid-request, the request never reaches the business layer: you get a real HTTP status code, and the body may not be JSON.

Always assert body.code === 200. Asserting res.status === 200 treats every business failure as a success.

Requests on port 80 are redirected to HTTPS with a 301, and a 301 does not preserve the POST body — use https:// directly.

3. Authentication and Signing#

Every request carries four headers:

Header Description
x-api-key Your app_key
x-timestamp Timestamp in milliseconds (13 digits); must be within 5 minutes of the server clock (either direction)
x-nonce Random string matching ^[A-Za-z0-9._:-]{8,128}$; the same nonce can be used only once per merchant within 10 minutes (see 3.2)
x-sign HMAC-SHA256 as lowercase hex; see 3.1

3.1 Signature Algorithm XPIN-KV1#

What gets signed is the parsed data, not the raw bytes of the message — so you can send the body with any JSON library, key order or indentation, and you do not need to control the exact bytes your HTTP client sends. The signed object always has these seven fields:

Build the base string from it with the four rules below, then compute hex(HMAC_SHA256(app_secret, base)).

R1 Flatten — recursively expand into a list of "path → scalar" pairs:

  • Nested objects: join path segments with .. {"data":{"code":"X"}} → path data.code
  • Arrays: the index is a segment. {"tags":["a","b"]} → tags.0, tags.1
  • An empty object yields one entry path → o:, and an empty array yields one entry path → a:. Without this marker, {"a":{}} and {} would produce the same base string
  • Keys must match ^[A-Za-z][A-Za-z0-9_]*$. Reject any key that does not; do not try to escape it

R2 Value encoding (with type tags):

Value Encoding
String s: + raw text (UTF-8, no characters escaped)
Integer i: + decimal, no leading zeros, -0 written as 0
Boolean b:true / b:false
null n:

Numbers must be integers with an absolute value ≤ 2⁵³−1 (2 and 2.0 are both treated as integers). Decimals, out-of-range integers, NaN and Infinity are always rejected — do not try to encode them. Request bodies for this channel only contain pageNo, pageSize and productCode, so normal use never hits this rule. There are also two structural limits: nesting depth 8 and 512 leaves in total; exceeding them yields CANONICAL_TOO_DEEP and CANONICAL_TOO_LARGE respectively (both 400).

R3 Literal for each entry (length-prefixed):

⚠️ The length is the byte count of the whole encoded value, including the two-character type tag s: / i:. "ak_demo" encodes to s:ak_demo, whose length is 9, not 7 — this is the most common implementation mistake.

R4 Sort and join — sort ascending by the UTF-8 bytes of the full path and join with &.

3.2 nonce#

⚠️ Use a truly random value for x-nonce — not a timestamp, and not a digest of the body. If the nonce equals the timestamp, a client that swaps the two arguments by mistake cannot be caught by the signature.

Deduplication key and window: nonces are deduplicated per environment + merchant + nonce and remembered for 10 minutes. Random nonces satisfy this naturally; you do not need to maintain a pool.

3.3 Authentication Check Sequence#

When several conditions fail at once, you only see the first one hit:

Step 8 is deliberately separate from SIGNATURE_INVALID: it means the payload contains a value that cannot be signed, not that your key is wrong. If you see CANONICAL_*, check the payload, not the key.

Quota: /products/list and /products/detail together allow at most qpsLimit requests per second, configured by the platform for your account. Exceeding it returns 429 QPS_LIMITED; back off and retry. When syncing the full catalog, page through serially rather than in parallel.

Two properties follow from this sequence and are useful for troubleshooting:

  • A nonce is consumed only when the request would otherwise succeed (step 11 is last). So retrying with a bad signature always returns SIGNATURE_INVALID, and your own retries never turn into NONCE_REPLAYED.
  • Parameter validation happens before authentication. A missing required field gives you 400 xxx required, not 401.

5. Plan Object DataPlan#

Field names, types and enums all match the DataPlan of eSIMDB Provider API v1.0.2, and the five required fields (validity, dataCap, dataUnit, prices, coverages) are present on every plan object.

5.1 Fields#

Field Type When present DataPlan spec Description
planName string Always Optional Plan name, truncated beyond 100 characters
validity integer Always Required Plan duration in days
dataCap integer Always Required High-speed data allowance; for daily plans, the allowance per day. See §5.2
dataUnit string Always Required MB or GB
dataCapPer string Daily plans only Optional Always day. Not returned for total-allowance plans, meaning the allowance does not reset per period
reducedSpeed integer Only plans throttled after the allowance Optional Speed limit after the high-speed allowance is used up, in kbps. Absent means the connection is cut off when the allowance is used up
prices object Always Required Price. Keys are ISO 4217 currency codes; values are JSON numbers (not strings). Currently only USD
link string When a purchase page is configured Optional URL of this plan's page on the purchase platform. Already URL-encoded; use it as-is — do not parse or rebuild it
capacityInfo string When there is a note Optional Note on the data rules, e.g. 50GB high-speed data, stop when used up
coverages array Always Required Covered countries, ISO 3166-1 alpha-2. The two forms are described in §5.2
subscription boolean Always Optional Always false: the platform has no auto-renewing plans
promoEnabled boolean Always Optional Always false: the platform does not accept promo codes. DataPlan defaults this field to true, so it is stated explicitly

5.2 Value Rules#

Data allowance: dataCap / dataUnit / dataCapPer#

Plan dataCap dataUnit dataCapPer Example
Total-allowance plan High-speed data for the whole validity period Always MB Not returned 50GB plan → 51200 / MB
Daily plan High-speed data per day GB or MB day 2GB per day → 2 / GB / day
  • Total-allowance plans are given in MB, not converted to GB: dataCap must be an integer, and 1536MB is 1.5GB, so rounding would overstate or understate the allowance by half a gigabyte.
  • dataCap is never 0: in DataPlan, 0 means truly unlimited, and no plan in the current catalog is. Daily plans marketed as Unlimited are "N GB of high-speed data per day, then throttled"; they are returned as in the table above, with the throttled speed in reducedSpeed.

Throttling: reducedSpeed#

  • Daily plans: once the day's high-speed allowance is used up, the speed drops to this rate in kbps (for example 512); high speed resumes the next day.
  • Total-allowance plans: the connection is cut off when the allowance is used up, and this field is not returned. In DataPlan, its default null means exactly that: cut off when used up.

Coverage: coverages#

DataPlan allows two forms, and each plan uses one of them. Both appear in responses, so support both:

Form When used Example
Array of country codes Always for multi-country plans; also for single-country plans without reliable operator information ["CA", "MX", "US"]
Array of objects Single-country plans whose operators can be confirmed [{"code": "ID", "networks": [{"name": "Telkomsel"}, {"name": "XL"}]}]

In the object form, networks only has name and no types (3G/4G/5G): the platform has no network-technology data and does not make one up.

Other fields#

  • prices: the price, as a JSON number. All plans currently use a single currency, USD.
  • link: the product-code part is already URL-encoded (for example / becomes %2F); use it as the redirect URL as-is. Plans without a configured purchase page do not return link — the platform never returns a link that does not open.
  • planName: the plan's public name, truncated beyond 100 characters.

5.3 Fields Not Returned#

The platform does not return the other DataPlan fields; read them by their defaults:

Field Default Meaning for plans in this channel
hasAds / payAsYouGo / newUserOnly false No ads, not pay-as-you-go, not limited to new users
maxSpeed null No speed limit within the high-speed allowance
canTopUp / eKYC / tethering null Unknown: the platform has no data for these
telephony / internetBreakouts / subscriptionPeriod null / none Unknown: the platform has no data for these
priceInfo / validityInfo / additionalInfo None No additional notes
activationInfo — Deprecated in DataPlan; not returned

5.4 Examples#

Total-allowance plan: 50GB in total over 90 days, cut off when used up, so there is no dataCapPer or reducedSpeed.

Daily plan: 5 days, 2GB of high-speed data per day, then throttled to 512kbps.

6. Error Codes#

The table below lists the business codes the two endpoints in §4 can return. All of them arrive as HTTP 200 with the JSON envelope; the error code is in the body's code.

code msg Meaning What to do
200 ok Success —
400 <field> required / <field> length error [a-b] / <field> Range error / <field> Type error, ... Parameter validation failed (free text, not a stable error code) Fix the parameters. Match on code===400 plus the field name as a substring; do not match msg exactly
400 REQUEST_BODY_NOT_JSON / REQUEST_BODY_MUST_BE_OBJECT The body is not JSON, or is JSON but not an object Check the serialization
400 CANONICAL_* The payload contains a value that cannot be signed (decimal, out-of-range integer, invalid key, nesting too deep) Check the payload, not the key
401 AUTH_HEADERS_MISSING One of the four signature headers is missing Add the header
401 NONCE_INVALID Bad nonce format Use ^[A-Za-z0-9._:-]{8,128}$
401 TIMESTAMP_INVALID The timestamp is not a number or is off by more than 5 minutes Sync your clock; make sure you use milliseconds
401 APP_KEY_INVALID The app_key does not exist, is disabled, or does not match the environment Check the credential and the Base URL (sandbox credentials only work in the sandbox environment)
401 CREDENTIAL_EXPIRED The credential has expired Ask the platform to rotate it
401 SIGNATURE_INVALID Signature mismatch Run the self-test vectors in 3.5 first; once they all pass, debug the integration
401 NONCE_REPLAYED The nonce has already been used Use a new nonce for every request
403 SCOPE_FORBIDDEN The credential is not authorized for this endpoint Ask the platform to check the credential's permissions
403 IP_NOT_ALLOWED The source IP is not on the allowlist Ask the platform to add the IP
404 PRODUCT_NOT_FOUND The product does not exist or does not belong to you Check the productCode
404 — Misspelled path (correct prefix, wrong path name). msg is not a stable error code Check the path name
413 REQUEST_ENTITY_TOO_LARGE The request body exceeds 256KB Check the request body
415 CONTENT_TYPE_MUST_BE_JSON Content-Type is not application/json Fix the header
429 QPS_LIMITED Over the per-second request limit Back off and retry; page through serially for full syncs
406 [controller error] Server error; msg is a fixed string and carries no reason Back off and retry; contact the platform if it persists
501 FEATURE_NOT_IMPLEMENTED The requested endpoint is not available Check the path; the available endpoints are listed in §4
503 A platform-side reason code, e.g. OPENAPI_AUTH_UNAVAILABLE, PLATFORM_NOT_ENABLED A platform-side dependency or configuration problem, unrelated to your request Back off and retry, and pass the msg to the platform

Tenant isolation: "not found" and "not yours" return the same 404; the platform never tells you that a product exists but belongs to someone else.

6.1 Handling Non-200 Responses#

Some responses never reach the business layer. They carry a real HTTP status code, and the body may not be JSON:

You see Usually because
301 + non-JSON You used http://. A 301 does not preserve the POST body; use https:// directly
404 + non-JSON The path prefix is wrong (the correct prefix is /openapi/v1)
429 Abnormal request rate — back off and retry, and check your client for retry storms or loops
5xx / connection dropped Transport-layer or server error

⚠️ Do not treat every non-200 as retryable. Resending a 404 (wrong path) forever as a retryable error is one of the most common self-inflicted failures.
